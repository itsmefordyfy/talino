# DIRECTION (read first): Talino teaches how to BUILD SOFTWARE WITH AI

The owner's decision (2026-11-14): Talino is **not** a programming academy. Its identity is *"Learn to build software with AI, even
if you don't know how to code."* The audience is people who have never coded, students and entrepreneurs who want to turn ideas into
software, freelancers who sell AI-powered development, developers who want to be more productive, and professional engineers who
want to master agentic coding. Every course must help the learner **accomplish something real with AI**: generate a website from a
business idea, build a booking app, make a mobile app with a coding agent, connect a database by asking AI, fix a broken app with
Claude Code, improve a project with Cursor, have Codex implement a feature, deploy it, sell it. Courses end with a working project and
with the learner putting what they learned **into their own workflow** (their prompts, their instructions file, their checklist,
their routine).

- **Technologies are the tool, not the subject.** React, a database, an API, Expo, a server framework may appear because the AI uses
  them, but a lesson is about asking AI for it, understanding what was generated, changing it by prompt, fixing it with AI,
  testing and shipping it. Never write a lesson that is a tutorial on a language or framework. Teach the concept only as far as the
  learner needs to *understand and judge what AI produced*.
- **Teach the AI tools themselves** to everyone who needs them: do not assume a learner knows ChatGPT, Claude Code, Cursor, Codex,
  Copilot or Gemini because they know programming, and do not assume a complete beginner is unfamiliar with chat assistants.
- Structure is unchanged: explain, demonstrate, practise, then assess (the lesson contract below), now with the five-level adaptation.
- Product and pricing facts about AI tools change constantly: every such fact lives in a dated, sourced `version` note, and plans are
  described in words (never price figures).
- Ground the practical examples in AI-driven work: prompts (as `prompt` blocks the learner can copy), conversations, generated code to
  read and fix, specs, reviews, agent runs. You may show real, correct, runnable code (generated by an AI tool or written to be
  read), but the learner's job is directing, reading, checking and shipping.

# Writing a Talino course (brief for course writers)

You write ONE course of Talino's catalog as real teaching content, not an outline. Talino is a mobile learning app. Its
learners range from people who have never written a line of code to working developers, so every lesson must teach, then
check, then let the learner practise. Read this whole brief, then the files named under "Read first".

**Scope of your edits:** create exactly one file, `src/features/courses/content/catalog/courses/<course-id>.ts`.
Do not edit any other file in the repository. Scratch files (code you run to test examples) go in your scratchpad
directory (see your environment), never in the repo. Do not touch other apps or projects, and do not run `git`.

## The course file

```ts
import type { Course, Lesson, Project } from '../../types';

// Only volatile courses need this: const CHECKED = '2026-11-14';
const lessons: Lesson[] = [ /* one per syllabus topic */ ];
const projects: Project[] = [ /* 1 to 3 */ ];

export const <camelCaseId>Course: Course = {
  id: '<course-id>', kind: 'standard', title: '<exact syllabus title>', level: '<exact syllabus level>',
  tagline: '<one line, 15-110 chars>', description: '<2-3 sentences for the course page>',
  finishLine: ['<what the learner has/can do at the end>', ...],   // 2 to 5
  objectives: ['<verb-first learning objective>', ...],             // 3 to 6, each at least 4 words
  audiences: [...],        // from AudienceId in types.ts
  skills: [{ id: 'kebab-case', label: 'Label' }, ...],              // 3 to 10, every one taught by some lesson
  lessons, projects, icon: '<a Material Symbols name that exists in src/components/ui/material-symbols.json>',
  updated: '2026-11-14',
};
```

The export name is the course id in camelCase plus `Course` (`nodejs-express` -> `nodejsExpressCourse`,
`html-css` -> `htmlCssCourse`). No `coachRole`, `sponsor` or `path` fields. Write the file in pieces so no single
tool call is enormous: create it with the header, lessons 1-3 and a line `// @@MORE_LESSONS@@` before the closing `];`, then
add lessons with the Edit tool at that marker, and remove the marker at the end. **Write each lesson complete, quiz included, before starting the next** (no placeholder stubs: they hide problems until the end). Run the check often (below).

## Every lesson, in this order

Lesson data (`Lesson` in types.ts): `id` (`<course-id>-NN`, two digits), `day`, `title` (exact syllabus title), `summary`
(one sentence), `minutes` (10 to 35), `skills`, `intro`, `body`, `quiz`, `task`.

1. **Introduction:** `intro.objectives` (2 to 4, verb-first: "Write...", "Explain...", "Spot...") and `intro.why` (why this
   matters to the learner's own goal, one or two sentences).
2. **Teaching, `body`** (about 500 to 900 words of explanation; the check demands at least 250 and the lesson must open with a
   `paragraph`): plain-language explanation first, **why before how**, then the idea, a concrete real-world analogy where it
   helps, then worked examples and code walkthroughs line by line. Use `heading`, `paragraph`, `list`, `code`
   (always with a `language` label), `table`, `tip`, `warning`, `details` (deeper "show more"), `diagram` (a Mermaid
   flowchart/sequence/class/ER diagram, or a validated JSON spec; check the examples in the AI-Assisted path), and
   `visual` blocks (interactive explainers; ids below). A lesson with a process, architecture or comparison should have a
   diagram or table. Do not decorate: a diagram must show the real mechanism.
3. **Version notes** (`{ type: 'version', text, checked: CHECKED, sources: [{ label, url }], plans? }`): for every statement
   that depends on a product, framework, API, command or standard version. Needed in most lessons of a `volatile` course
   (at least 60% of lessons). `checked` is `'2026-11-14'`. Sources are official https documentation pages you actually
   opened (hosts allowed are listed in `lib/path-rules.ts`). Name the version you verified ("React 19", "Next.js 16",
   "Python 3.14"); do not state price figures.
4. **Key takeaways:** exactly one `{ type: 'takeaways', items }` block (2 to 6 items) as the last teaching block.
5. **Activities** (`{ type: 'activity', activity }`): at least one per lesson, usually two. The app draws them AFTER the quiz,
   in the practice stage, so a lesson may place them anywhere in `body`, but put them after the takeaways in the file. Kinds:
   `tap-reveal`, `predict-output`, `fix-bug`, `arrange`, `fill-blank`, `match`, `scenario`, `code-challenge`, `sql-challenge`.
   Ids are `<lesson-id>-<kind>-<n>`. Each has 3 progressive `hints` (a nudge, a pointer, nearly the answer), an `explanation`
   that says why the answer is right, and, for wrong choices, notes that explain the mistake without giving the answer away.
   A `match` must make the learner apply an idea (situation to concept), never repeat a list printed just above.
   JavaScript activities are executed by the validator (outputs and tests are computed); for every other language you must
   run the code yourself and store the true output. Use code challenges where the subject is JavaScript or SQL; use scenarios,
   fix-bug and predict-output elsewhere. Mix kinds across the course.
6. **Quiz:** 3 to 5 questions, `id` `<lesson-id>-q<n>`, 3 or 4 choices, one `answer` index, an `explanation` of why it is right
   (and ideally why the tempting wrong choice is wrong). Test understanding and application, never trivia, never "all of the
   above". **Vary the correct answer's position** across questions (the check fails if over half share one slot). Every quiz
   question must be answerable from what the lesson taught: if you ask it, teach it.
7. **Task:** `{ title, steps (2+), minutes (5 to 20) }`, a small hands-on thing to do on a laptop.

Tali (the learner's companion) introduces the course and each lesson, introduces quizzes, hints and activities, and
celebrates results automatically from this data. **Do not write Tali dialogue or mascot references into the lessons.** Write
the way a patient teacher talks, in second person, short paragraphs, no jargon without a definition.


## Rules the checker enforces that are easy to miss

- **Activities** (`activities/lib/validate.ts`): every kind except `tap-reveal` needs at least 2 hints (3 is the target) with no empty or
  duplicate hint; `match` needs 3 or more pairs with unique terms and definitions; `scenario` needs exactly one option with
  `quality: 'best'`; a `predict-output` in any language except JavaScript needs `expected` (and `choices`, if given, must include it);
  for JavaScript the snippet is run by the app's own interpreter (a JavaScript subset, not Node), so keep snippets plain (loops,
  functions, arrays, objects, template strings, `console.log`) and let the validator be the judge. Keys of `wrongNotes` must be
  real wrong choices (the validator does not check this: you do). Quality is yours, not the checker's: a `match` that repeats a
  list printed just above it will pass the check and is still wrong.
- **The in-app JavaScript runner** (`src/features/code-runner/`) is a custom interpreter, not Node: no `Date`, regex literals beyond the basics,
  async code, `require`, `prompt` or the DOM. Each `console.log` call is ONE output entry (output tests compare an array of entries).
  A `fix-bug`/`fill-blank`/`code-challenge` with `tests` must fail for every wrong option, so never list two equivalent fixes (`==` next
  to `===` can both pass); the starter code must not already pass; robot grids count `y` downward. A function-style test needs the
  function to exist, so in a beginner course use an output-only challenge (or a provided function shell) until functions are taught.
- **Code blocks are syntax-checked** (`catalog/code-blocks.test.ts`): JavaScript, JSX/TypeScript/TSX, JSON, Python and bash blocks must parse with the real parser. A block that is deliberately a fragment (one piece of a component, several JSON messages in a row, a snippet with `...`) must say so in its `label` (include the word `fragment` or `pseudocode`), or use the language `text`.
- **Teach before you ask:** every term, operator or built-in a quiz question, activity or challenge uses must already have been
  taught in this or an earlier lesson (the check cannot see this: you must). Reread your activities for words the lesson never explained.
- **Hand-check list for activities** (nothing validates these automatically for non-JavaScript languages): `bugLine` is the 1-based line
  of the real bug; fix-bug replacement lines carry the original indentation; a fill-blank `bank` contains every `answers[0]`; every
  `wrongNotes` key is a real wrong choice; every stored `expected` was produced by actually running or rendering the code (for HTML/CSS a
  headless Chrome `--dump-dom` with the answer written to `document.title` works; for Python, `python3`; for bash, a scratch directory).
- **Template literals:** code stored in a TypeScript string must escape `${` as `\${` and backticks as `\``; prefer single-quoted strings
  with `\n` for short snippets, or a template literal with escapes for long ones.
- **`unlockAfterDay`:** a project opens when that lesson day is done. If the last lesson itself introduces the project, set
  `unlockAfterDay` to the lesson before it, not the final one, unless the project truly needs the whole course.
- **Version-note sources** may be reused across many notes; keep a `DOCS` constants object at the top of your file for the pages you cite
  often. Hosts by subject: language and web standards (developer.mozilla.org, w3.org, tc39.es, python.org, typescriptlang.org),
  frameworks (their own docs hosts, e.g. react.dev, nextjs.org, tailwindcss.com, flutter.dev, expo.dev), data (postgresql.org, mongodb.com,
  supabase.com, firebase.google.com), platforms (docs.github.com, docs.docker.com, learn.microsoft.com, cloud.google.com, aws.amazon.com),
  security (owasp.org, nist.gov, cisa.gov, ietf.org). Anything not on the list in `lib/path-rules.ts` fails; tell me if you need a host added.
- **Length:** 500 to 900 words of prose per lesson is the target for focus (a lesson is a 15 to 30 minute sitting). Going to about 1,100 for a
  beginner's first lesson on a hard idea is fine; going far beyond means the lesson should be split or tightened.
- **Mermaid subset** (`visuals/diagrams/mermaid.ts`): flowchart, sequence, class and ER only; no `subgraph`, `style`, `classDef`,
  `click`, `direction`, `&` joins or `---` links; no stadium or oval shapes (write start and end as `(rounded)` nodes); node labels
  up to 60 characters; at most 24 nodes; at most 6,000 characters. If you want something richer, use a `table`.
- **Quiz answers:** the check fails a course (8+ questions) where over half the right answers share a slot, and a course (10+) where
  the right answer is the single longest choice in over half the questions. Vary the slot from the first question and make wrong choices as
  specific and detailed as the right one.
- **Dates:** version notes use `checked: '2026-11-14'`, the date this catalog was written, so a future review knows when to recheck.
- Word counting: a lesson needs 250 teaching words (paragraphs, lists, tips, tables, `details`, version notes; code counts half). Aim for
  500 to 900 so beginners are never rushed.

## Level adaptation (REQUIRED for every course written from 2026-11-14 on)

Talino has five learner experience levels (complete-beginner, beginner, intermediate, advanced, professional: programming
experience, not AI-tool experience). Read docs/content/ADAPTATION_BRIEF.md now: your course must carry the level pieces from
the start, written as you write each lesson, not bolted on afterwards. Minimum per lesson: one plain-language block for
newcomers (`audience: { max: 'beginner' }`), one depth block for experienced learners (`audience: { min: 'advanced' }`), one
quiz question for each side (extra ids `-q5`, `-q6`, tagged), a `taskExtra`, and in every project `audience` steps and
`rubricExtra`. The shared lesson still has to stand alone (250 words of shared teaching; each learner is asked 3 to 6 quiz
questions). `lib/standard-rules.ts` (`levelAdaptationProblems`) enforces it. Courses already written before this requirement
are exempt (`NOT_YET_ADAPTED`) and are adapted later.

## Beginner courses (level `beginner`)

Assume the learner has never coded. Define every term the first time it appears, in everyday words. Use relatable examples
(a shop, a recipe, a group chat, a school queue). Introduce one new idea at a time. Show a small example before a big one.
Hints before answers. Never show a wall of code: build it in steps and explain each line. Advanced courses keep real depth,
with clear explanations and honest trade-offs.

## Truth and accuracy (the most important rule)

- Verify every technical claim, command, flag, API, version and number against **official documentation**. You have web tools:
  load them with ToolSearch (`select:WebFetch,WebSearch`) and open the real pages. If you cannot confirm something, leave it
  out or say what is uncertain. Never invent a URL, a version, a feature or a quote.
- **Run every code example** you can (`node`, `python3`, `sqlite3`, `psql`, `dotnet` are installed; TypeScript can be checked with
  `npx tsc` from the repo). Code in a lesson must be correct, idiomatic for the version taught, and secure (no hardcoded secrets,
  parameterised queries, validated input). A predict-output answer you did not run is a bug.
- Do not copy text from docs or books; explain in your own words. Short code that the docs themselves show can be adapted.
- Date-stamp anything that changes. The AI and framework worlds move quickly: prefer teaching the stable idea, and put the
  version-specific detail in a `version` note so a future review knows what to re-check.
- Philippine learners are a main audience: examples can use pesos, jeepneys, sari-sari stores, local apps and names, but never
  real people, real companies' private data, or stereotypes. Stay region-neutral where the topic is global.

## Projects

1 to 3 per course, id `<course-id>-p<n>`; the last opens after at least 70% of the lessons (`unlockAfterDay`). Each has a
`title`, `summary`, `outcome` (the proof it gives an employer or client), 3+ `steps` (`<project-id>-s<n>`; a `link` only to an
official page), a `submission` (`url` for a repo or live link, `text` for pasted work, with `label`, `placeholder`, `hint`)
and a `rubric` of 3 to 6 things a reviewer checks. The project is the course's final practice: it should use what the
lessons built.

## Check your work, then report

```bash
CHECK_COURSE=<course-id> npx jest src/features/courses/content/catalog/check-one
npx tsc --noEmit   # no errors in your file
```

Both must pass with no problems listed. Fix every problem the check prints. Then re-read your own lessons once as a learner
would: does each one teach before it asks? Is any quiz question unanswerable from the text? Is any code wrong or any claim
unverified? Fix what you find.

Finish with a short report: lessons written, activities by kind, version notes count, the sources you relied on (titles),
anything you were unsure of and how you handled it (cut it, hedged it, or flagged it), and any overlap with another course
you noticed. Be honest about what you could not verify.
