# Data Structures and Algorithms: brief for module writers

**Course:** `data-structures-algorithms`, "Data Structures and Algorithms: From Fundamentals to Practical Problem Solving" (intermediate, 72 lessons in 19 modules).
**Owner's brief (2026-11-16):** a practical course on how software organizes, stores, retrieves and processes data efficiently. The aim is not to memorise
structures: learners must understand how each works internally, when to use it, its performance trade-offs and how to apply it in real applications, and
they must be able to use an AI coding assistant to understand, implement, test and optimize algorithms **without it replacing their own reasoning**.
It builds on Programming Fundamentals (recommended prerequisite, never required: the learner may not have taken it) and complements object-oriented
programming (not required: classes are taught in one paragraph where first needed, see below). It is the second deliberate exception to Talino's
"no standalone programming course" rule (CLAUDE.md): choosing a structure and judging an algorithm's cost is what lets a learner direct and review AI-written code. JavaScript is the practice language (the in-app code runner
runs it; say that the ideas carry to every language); TypeScript appears only in short optional `details` blocks where types make a structure clearer (they are not runnable in the app: label them `fragment`).
No browser, DOM, framework, HTML, Node-only API or backend (other Talino courses cover those); the web and mobile examples of module 17 are about the *data* those apps hold, shown in plain JavaScript.

You write one or two **modules** (your assignment says which). **First read, in this order:** `docs/content/WRITING_BRIEF.md` (the lesson contract, activity rules, accuracy
rules; its "DIRECTION" paragraph about AI-first still holds: here the technology is JavaScript as a teaching language), `docs/content/ADAPTATION_BRIEF.md`
(five learner levels: every lesson still needs the level pieces), `src/features/courses/content/types.ts`, `lib/lesson-structure.ts`, `lib/standard-rules.ts`,
`src/features/activities/types.ts` and `lib/validate.ts`, the in-app runner `src/features/code-runner/` (what it supports: it supports classes, `Map`, `Set`,
`for...of`, array methods, `JSON`, `Math`; not `Date`, `Symbol`, `RegExp`, async, modules), the syllabus `src/features/courses/content/catalog/syllabus-dsa.ts` (your lesson titles, copied exactly), and for

## The shape of every lesson (the owner's ten parts)

Each lesson's `body` is, in this order (headings are literal strings so a learner always finds the same parts; the module check enforces them):

1. **Opening paragraph**: what this lesson is about and why it matters to someone who will build with AI (the lesson must open with a `paragraph`). `intro.objectives` (2 to 4, verb-first) and `intro.why` carry the learning objectives.
2. `heading` **"A real-world picture"** then a paragraph or two: an everyday analogy (a sari-sari store, a jeepney route, a recipe, a queue, a group chat, a school bell). Keep it honest: say where the analogy stops working.
3. `heading` **"How it works"** then the concept explained plainly, **why before how**, one idea at a time, terms defined at first use. Include a visual wherever it teaches: a `diagram` (Mermaid flowchart/sequence, or a JSON spec) or a `visual` from the library (the DSA ids listed below; the check rejects an id that does not exist) or a `table`. A diagram must show a real mechanism, never decorate.
4. `heading` **"See it in code"** with `code` blocks (language `javascript`, built in small steps, never a wall), then `heading` **"Walk through the code"**: what happens line by line when it runs (a `list` or paragraphs; for loops and state, a step-by-step trace table with `table`). Lessons that show no code (some of modules 1 and 2) replace these two headings with **"Walk through an example"** (for example tracing an algorithm step by step on paper). The check accepts either pair.
5. Level pieces (see ADAPTATION_BRIEF): a plain-language block `audience: { max: 'beginner' }` right after the concept it explains and a depth block `audience: { min: 'advanced' }`. Also `tip` / `warning` / `details` blocks where they earn their place.
6. `heading` **"Try it with AI"**: the AI-assisted exercise. At least one `prompt` block the learner copies into any AI assistant (ChatGPT, Claude, Gemini: the learner may use whichever they have; teach the tool only as far as this lesson needs, never assume it), followed by a short paragraph or list on **what to look for in the answer** and one way the answer might mislead (an AI can be confidently wrong). Early lessons use "explain it in plain words / give me one more example / quiz me"; later lessons use "generate, then explain line by line, then find the bug". Never tell the learner to paste secrets or personal data. Do not hand over exercise answers through the prompts: ask the AI to guide, hint and check, not to solve (write prompts like "Do not give me the answer; ask me questions").
7. **Key takeaways**: exactly one `takeaways` block (2 to 6 items), the last teaching block: the lesson summary.
8. **Activities** after the takeaways (they are drawn after the quiz): at least **two** per lesson, of different kinds, with ids `<lesson-id>-<kind>-<n>`, three hints each, an explanation, and `wrongNotes`/feedback that explain a mistake without giving the answer away. The owner's list is the menu, and across a module you should use all of it: **predict the output** (`predict-output`), **trace algorithm execution** (a `fill-blank` or `predict-output` over a trace in a `code` block or a `table`: what the array, stack, queue, pointers or call stack hold after each step; there is no separate trace kind), **identify the appropriate data structure** (`scenario` or `match`: situation to structure), **complete missing code** (`fill-blank`), **fix an incorrect implementation** (`fix-bug`), **compare complexity** (`match` or `predict-output`: operation counts or Big O labels), **analyze a real-world scenario** (`scenario`), **optimize an inefficient solution** (`code-challenge` whose hidden tests include a larger input, or `scenario`), **implement a structure from scratch** (`code-challenge`: a small class or function set with hidden tests), `arrange` (steps of an algorithm or lines of code in order) and `tap-reveal`. Every activity must be real: the validator runs JavaScript, so run everything.
9. **Quiz** (the knowledge check): 3 to 5 shared questions that test understanding and application, not recall, plus the level-tagged `-q5` / `-q6` questions (ADAPTATION_BRIEF). Vary the correct answer's position; the right answer is not the longest choice; every question answerable from the lesson.
10. **Task** (the hands-on activity: 5 to 20 minutes on paper or a laptop, anything runnable by the learner in any free JavaScript environment or on paper) plus `taskExtra` for levels.

Length: 500 to 900 words of explanation per lesson (up to about 1,100 for a first lesson on a hard idea), `minutes` 15 to 30. Teach before you ask: every term, operator or built-in used in a quiz, activity or challenge must have been taught in this or an earlier lesson of the course (the order is the syllabus order; **you may not use any idea that a later lesson teaches**, and you may rely on every earlier lesson). If a lesson needs an idea that comes later, show it as a black box ("this line prints a value; the next module explains how") or leave it out. Do not re-teach an earlier lesson: refer to it by name.


## Voice and content rules

- English only. Do not write Tagalog or Filipino text (a standing owner rule). Examples may use pesos, jeepney routes and fares, sari-sari stores, barangay events, school queues and Filipino names, never real people or companies' private data, never stereotypes; stay neutral where the idea is global.
- Second person, short paragraphs, a patient teacher. No Tali dialogue or mascot references. No condescension, no jargon without a definition. One new idea at a time, a small example before a big one, hints before answers. **Understanding, not memorisation:** every "how" comes with the "why", and every complexity claim is shown by counting operations on a small example before the Big O name is attached (never present Big O as a formula to memorise).
- **Accuracy is the first rule.** Run every JavaScript example with `node` and keep the real output; the in-app runner is a subset, so also let the validator run activities. State complexities precisely (average vs worst case; amortized where it applies; JavaScript `Array.prototype.shift`/`unshift`/`splice` are O(n) in the model the lesson uses, and engines optimise, so say "in the model we use" where it matters; a JavaScript `Map` and `Set` give average O(1) operations, and the language specification only requires sub-linear time). Do not claim an engine's internal implementation unless the specification or official documentation says so. Verify any claim about a tool, command or standard on official pages (WebFetch/WebSearch: `ToolSearch` with `select:WebFetch,WebSearch`); allowed documentation hosts are in `src/features/courses/lib/path-rules.ts`. This is a stable subject, so version notes are optional; where one is warranted (an AI assistant's features, a JavaScript behaviour that changed) add a `version` note with `checked: '2026-11-16'` and official https sources you opened, no price figures.
- Never invent a URL, version, quote or statistic. Say what is uncertain or leave it out. Use established computer science curricula (the foundational structures, complexity analysis, searching, sorting, recursion, trees, heaps, hashing, graphs) for completeness and technical accuracy, but write original explanations, examples and questions: copy nothing.
- JavaScript style: `const` by default, `let` when a value changes, `===`, template literals, semicolons, 2-space indentation, `console.log` for output (each call is one output entry in the runner). **Classes** are allowed from lesson 17 (linked lists) on: introduce the syntax in one short paragraph there ("a class is a blueprint that creates objects with the same shape and methods; that is all you need here"), and before lesson 17 use plain objects and functions. No `prompt()`, no `Date`, no async, no modules, no DOM, no `RegExp`.
- **Running example threads:** customers (`{ id: 101, name: 'Aling Nena', city: 'Naga' }`) in the early modules, products for inventory (`{ sku: 'SKU-001', name: 'Instant coffee', qty: 40, price: 7 }`), playlists, support tickets, tasks (`{ id: 1, title: 'Pay electric bill', priority: 2, due: '2026-11-20', category: 'home' }`, dates as plain strings that sort correctly), and jeepney or barangay maps for graphs. The final project (module 19) is the task manager: do not build it early.
- Code blocks are syntax-checked (the real parser): a deliberate fragment or pseudocode needs the word `fragment` or `pseudocode` in its `label`, or language `text`. Escape `${` and backticks inside TypeScript strings.
- Never a wall of code: build up in steps, explain every line. A learner who skipped Programming Fundamentals must still follow: recap an idea you rely on (loops, functions, `Map`) in one sentence, referring to Programming Fundamentals by name for more, and never re-teach it at length.
- Do not copy text from docs or books; explain in your own words.
- **AI is a partner, never a substitute.** Every "Try it with AI" prompt asks the AI to explain, quiz, hint, review or check; prompts for generated code always require the learner to predict or read first, and always ask for the complexity and for tests. In module 18 the rule is explicit: the learner states their own answer before asking.

## Module notes (what each module must cover: every bullet of the owner's curriculum appears in some lesson)

**Lessons per module and their days:** M1 days 1-4, M2 5-9, M3 10-13, M4 14-16, M5 17-20, M6 21-23, M7 24-26, M8 27-30, M9 31-33, M10 34-37, M11 38-40, M12 41-43, M13 44-48, M14 49-51, M15 52-56, M16 57-61, M17 62-64, M18 65-68, M19 69-72.

1. **Introduction.** What data structures and algorithms are and why they matter; how computers store and process data (memory as numbered cells, values and addresses in plain words, CPU and memory, why layout affects speed); data types vs data structures; abstract data types (what vs how: a stack is an idea, an array or a linked list implements it); linear vs non-linear; static vs dynamic; algorithm efficiency (operation counts, informally, no Big O yet); choosing the right structure (a decision table). Practical activity (lesson 4's task): compare ways to store and retrieve customer records (an unsorted array, a sorted array, an object keyed by id) by counting how many records are looked at to find one customer; no Big O yet.
2. **Complexity.** What complexity is (count steps, not seconds); time and space; Big O notation as "how the count grows", dropping constants and lower terms, with each of O(1), O(log n), O(n), O(n log n), O(n²) shown by counting; best, average and worst cases; growth rates; analyzing nested loops; comparing two solutions; amortized analysis (the dynamic array doubling, the classic). Use the `big-o-growth` visual and your own operation counters in code (`let steps = 0`) rather than timing. Lesson 8's task is the practical activity (two implementations of searching, count checks as n grows).
3. **Arrays.** Contiguous storage and why indexing is O(1); accessing, updating, inserting and removing (shifting, with counts); traversing; searching; multidimensional arrays (grids, rows and columns, row-major reading); dynamic arrays (resizing, amortized O(1) append); operations and their complexity (a table); problem patterns (running totals, in-place updates, two passes, the first look at two pointers). Visual `array-operations`. Project p1.
4. **Strings.** Strings as sequences of characters, immutable in JavaScript (so building a long string by repeated `+=` is worth discussing honestly, without claiming engine internals); indexing; traversal; concatenation; searching (a naive substring search written by hand, counting comparisons, then `includes`/`indexOf` as the built-ins); reversal (and why `split('').reverse().join('')` works and its limits); palindromes (two pointers; ignoring case and spaces); character frequency counting with an object or `Map`; anagram checks; a few common string algorithms (first non-repeating character, longest common prefix). Project p2.
5. **Linked lists.** Nodes and references (classes introduced here, see above); arrays vs linked lists (a trade-off table: indexing, insert/remove at the front, memory); singly linked list with head (append, prepend, insert after, remove, search, traverse, length); doubly (prev and next, remove given a node in O(1)); circular; reversing a list in place (the three-pointer loop, traced); detecting a cycle (Floyd's slow and fast pointers); complexity of each operation. Visual `linked-list`. Project p3.
6. **Stacks.** LIFO, push, pop, peek, isEmpty; array-backed and linked-list-backed implementations; complexity (all O(1)); balanced parentheses; undo/redo with two stacks; evaluating a postfix expression (and a short note that infix needs more); the call stack as a stack (forward pointer to module 9). Visual `stack-lifo`. Project p4.
7. **Queues and deques.** FIFO, enqueue, dequeue; an array-backed queue (and why `shift` is the slow part in our model), a linked-list queue, a circular queue with head, tail and size; the deque (both ends); a first look at priority queues (a sorted insert, to be replaced by a heap in module 11); complexity; real-world queues (print jobs, customer tickets, a breadth-first frontier); task scheduling (first come first served, round robin). Visual `queue-fifo`. Project p5.
8. **Hash tables, maps and sets.** What hashing is and what a good hash function does (deterministic, spread out, fast); a toy string hash with modulo; key-value storage; collisions and the load factor; separate chaining and open addressing (linear probing) written from scratch; complexity (average O(1), worst case O(n)); JavaScript `Map`, `Set` and plain objects: when each fits (key types, insertion order, size, prototype keys, iteration); removing duplicates with a `Set`; counting with a `Map`. Visual `hash-table-collisions`. Project p6.
9. **Recursion.** Base case, recursive case, the call stack (trace a call), factorial, Fibonacci, sum of an array, countdown; recursion vs iteration (and when the loop is better); common mistakes (no base case, base case never reached, repeated work, stack overflow: the runner has a depth limit, say so); memoization (Fibonacci before and after, with call counts); an introduction to backtracking (choose, explore, un-choose, on a tiny problem such as printing the binary strings of length 3). Visual `recursion-call-stack`. Lesson 33's task is the practical activity.
10. **Trees.** Terminology (root, parent, child, sibling, leaf, depth, height, subtree); binary trees as nodes with `left` and `right`; representation (nodes with references; an array form is met again in module 11); the four traversals (the three depth-first orders recursively, level order with a queue); binary search trees (the ordering rule, search, insert, delete with its three cases, the cost O(h)); balanced vs unbalanced (inserting sorted data into a BST gives a chain; name self-balancing trees such as AVL and red-black trees in words only); hierarchical data (a file and folder tree, an org chart, nested categories). Visual `binary-search-tree`. Project p7.
11. **Heaps.** The heap property and the complete-tree shape; min-heap vs max-heap; array representation (the parent and child index formulas, with a table); insertion (sift up) and removal of the root (sift down); heapify (building a heap from an array in O(n), stated and demonstrated, with an honest note on why); heap sort (and its cost O(n log n), in place); a priority queue built on a heap (peek O(1), insert and extract O(log n)); applications (task scheduling, top-k, merging). Visual `heap-operations`. Project p8.
12. **Tries and specialized structures.** A trie as a tree of characters with an end-of-word flag; insert and search; prefix matching and counting; autocomplete (collect all words under a prefix, limit and rank them); memory trade-offs against a `Set` of words; union-find (parent array, find with path compression, union by rank or size, a use: connected groups of friends or computers); when to use a specialized structure and when a plain array, `Map` or `Set` is enough. Visuals `trie-autocomplete`, `union-find`. Project p9.
13. **Graphs.** Vertices and edges; directed and undirected; weighted and unweighted; cyclic and acyclic; adjacency matrix vs adjacency list (a trade-off table: space, edge look-up, neighbours); BFS (queue, shortest path in an unweighted graph) and DFS (stack or recursion); detecting cycles (undirected with a parent, directed with three states); connected components; shortest paths introduction; Dijkstra's algorithm (a simple version scanning for the smallest distance, then mention a priority queue; non-negative weights only, and say why); topological sorting (Kahn's algorithm, with a task-dependency example). Visuals `graph-bfs-dfs`, `graph-shortest-path`. Project p10.
14. **Searching.** Linear search; binary search (iterative, the invariant, the midpoint without overflow note: `Math.floor((low + high) / 2)` is fine in JavaScript, explain the classic overflow issue in other languages in a `details`), why it requires sorted data (an activity where it fails on unsorted input), variations (first and last occurrence, lower bound, search on a rotated array only as a `details`, search on an answer); searching sorted data; searching in trees (a BST search); hash-based search; comparing algorithms by counting checks. Visual `searching-linear-binary`. Lesson 51's task is the practical activity (several searches, counted).
15. **Sorting.** Why sorting matters (it makes binary search, grouping and merging possible); bubble, selection, insertion (with the early exit and the nearly-sorted case); merge sort (divide, merge, O(n log n), O(n) extra space); quick sort (partition, pivot choice, the O(n²) worst case, average O(n log n)); heap sort (from module 11, compared); counting sort and radix sort as introductions (not comparison based, when they apply); stable vs unstable (a stability demonstration on records with equal keys); in-place vs out-of-place; a comparison table of time and space; JavaScript's own `sort` (its default compares as strings: the famous `[10, 9, 1].sort()` trap, and passing a comparator; the language requires `sort` to be stable since ES2019, which you should confirm in the specification or MDN). Visuals `sorting-algorithms`, `sort-extra`. Project p11.
16. **Patterns.** Breaking a problem down (restate, examples, brute force first, then improve); two pointers; sliding window (fixed and variable); prefix sums (range sums in O(1)); frequency counters; fast and slow pointers; binary search patterns; divide and conquer; greedy algorithms (coin change with a canonical coin set and a counter-example where greedy fails: honest about when greedy is correct); backtracking (subsets, permutations, with pruning); dynamic programming introduction (overlapping subproblems and optimal substructure; climbing stairs, a small knapsack or coin-change count), memoization (top down) vs tabulation (bottom up). Start with beginner-friendly examples and raise the difficulty lesson by lesson. Use `recursion-call-stack` for memoization where it fits.
17. **Real applications.** Realistic web and mobile data examples in plain JavaScript: list state in an app (immutable updates: copying an array with spread, why re-rendering libraries like new references: one honest paragraph without teaching a framework); Maps for fast lookups (a cache by id, normalized state: `byId` and `allIds`); Sets for removing duplicates and membership; queues for background tasks (a retry queue, an upload queue); stacks for undo and navigation history (a back stack); trees for hierarchical data (comments, menus, folders); tries for search suggestions; graphs for social networks and navigation (friend suggestions, routes); heaps for scheduling and prioritization (notifications, top-k); data structures in backend services (an in-memory cache with an eviction rule such as LRU using a `Map`, rate limiting with a sliding window, indexes as sorted or hashed structures, in words); choosing structures for large datasets (when data does not fit in memory: paging, streaming, indexes, in words); performance and memory trade-offs (time vs space, a table).
18. **AI-assisted algorithm development.** The learner is the reasoner and AI is the partner. Lessons: asking an AI to explain an algorithm (and checking the explanation by tracing it yourself), choosing a structure with AI (state your constraints first: operations, sizes, ordering; ask for trade-offs, then decide); generating an implementation (read first, predict, then run: ask for comments and tests), understanding generated code (line-by-line, trace with a small input, ask what each line is for); asking AI to analyze time complexity (then derive it yourself by counting and compare; common AI mistakes: confusing average and worst case, ignoring the cost of built-in methods such as `includes`, `indexOf`, `splice`, `slice`, `shift`, spreading, and string concatenation in a loop); comparing multiple solutions; finding performance bottlenecks (count operations, find the nested scan, replace the repeated search with a `Map` or `Set`; measure by counting); debugging algorithm implementations (off-by-one, wrong base case, mutating while iterating, comparing objects by reference, mishandled empty input); generating edge cases and testing correctness (empty, one element, duplicates, sorted, reversed, large; property-style checks such as "the output is sorted and has the same elements"); detecting incorrect AI explanations (confident but wrong complexity claims, a wrong invariant, an unstable sort called stable, binary search on unsorted data, a hash map called always O(1)); reviewing AI-generated optimizations (does it keep the behaviour, is it faster by count, is it still readable, did it change the output order).
