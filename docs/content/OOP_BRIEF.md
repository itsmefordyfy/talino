# Object-Oriented Programming: brief for module writers

**Course:** `object-oriented-programming`, "Object-Oriented Programming: From Fundamentals to Practical Software Design" (intermediate, 80 lessons
in 14 modules). **Owner's brief (2026-11-16):** teach learners to organise code into objects and classes and to design maintainable, reusable
software; the concepts must transfer, so the course is **concept-first and language-independent**. JavaScript is the practice language (the
in-app runner executes classes, `#private` fields, getters/setters, `static`, `extends`/`super`, `instanceof`, `Error` subclasses and
`try/catch/finally`); TypeScript appears where a compile-time idea needs it (access modifiers, interfaces, abstract classes); short comparisons
with Java, Python and C# appear only where they make a difference visible. It is the **second deliberate exception** to Talino's "no standalone
programming course" rule (Programming Fundamentals is the first): the architecture AI tools generate is built from these ideas, and the learner
has to read, direct and judge it. So it is not a JavaScript or framework course. No browser, DOM, framework, database or server code is run
here (Module 12 *describes* where objects appear in those; any snippet there is a small, framework-free illustration).

**Prerequisite:** Programming Fundamentals (variables, conditions, loops, functions, scope, arrays, objects as key-value pairs, `Map`/`Set`,
debugging, basic tests, an AI assistant as a partner). Do not re-teach it: link to it by name ("the Programming Fundamentals course covers this").
The learner has **not** met classes, `this`, `new`, constructors, TypeScript, interfaces or UML before this course.

You write ONE module. **First read, in this order:** `docs/content/WRITING_BRIEF.md` (lesson contract, activity rules, accuracy rules; its AI-first
"DIRECTION" paragraph still holds in spirit), `docs/content/ADAPTATION_BRIEF.md` (five learner levels; this course's audience is mostly
beginners and intermediate learners, but every lesson still needs the level pieces), `docs/content/PROGRAMMING_FUNDAMENTALS_BRIEF.md` (the lesson
shape this course shares, and how a module file is built), `src/features/courses/content/types.ts`, `lib/lesson-structure.ts`,
`lib/standard-rules.ts`, `src/features/activities/types.ts` and `lib/validate.ts`, the in-app runner `src/features/code-runner/` (and
`language.test.ts` for what classes support), the existing interactive visuals `src/features/visuals/oop/` (ids `classes-objects`, `encapsulation`,
`abstraction`, `inheritance`, `polymorphism`: reuse them with a `visual` block where they teach), and for craft one finished course:
`src/features/courses/content/catalog/courses/ai-coding-beginners.ts`. The archived `docs/content/archive-programming-courses/oop.ts.txt` is raw
material from an earlier, smaller OOP course: you may adapt ideas and good examples, never paste; your lessons use the structure below.

## The shape of every lesson (the ten parts, same as Programming Fundamentals)

`body`, in this order, with these literal headings so a learner always finds the same parts (the check enforces them):

1. **Opening paragraph**: what the lesson is about and why it matters to someone who will build, read or review software (it must be a `paragraph`). `intro.objectives` (2 to 4, verb-first) and `intro.why`.
2. `heading` **"A real-world picture"**: an everyday analogy (a sari-sari store, a jeepney route, a barangay office, a recipe, a school ID, a remote control). Say where the analogy stops working.
3. `heading` **"How it works"**: the concept plainly, **why before how**, one idea at a time, terms defined at first use. Add a visual wherever it teaches: a `diagram` (Mermaid `classDiagram`, `flowchart` or `sequenceDiagram`, or a JSON spec), a `visual` from the library, or a `table`. A diagram must show a real mechanism (a class diagram of the real classes in the lesson, a sequence diagram of the real call, an inheritance tree, a before/after architecture), never decorate. **Class-diagram notation, the same in every module:** members `+public`, `-private`, `#protected`, methods with `()`; inheritance `Parent <|-- Child`; implements/realizes an interface `Interface <|.. Class`; composition `Whole *-- Part`; aggregation `Whole o-- Part`; association `A --> B`; dependency `A ..> B`; `<<interface>>` and `<<abstract>>` annotations. Check the subset the app draws in `src/features/visuals/diagrams` (`parseMermaidSubset`, `validateDiagram`) and that your diagram renders.
4. `heading` **"See it in code"** with `code` blocks (language `javascript`, or `typescript` where the lesson is about a compile-time idea; built in small steps, never a wall), then `heading` **"Walk through the code"**: what happens line by line when it runs (a `list`, paragraphs, or a trace `table` for state changes and call order; for a method call, say which object `this` is). A lesson with no code (pure design discussion) replaces both headings with **"Walk through an example"**.
5. Level pieces (ADAPTATION_BRIEF): a plain-language block `audience: { max: 'beginner' }` right after the concept it explains, and a depth block `audience: { min: 'advanced' }` (trade-offs, how it looks in a large codebase, testing, failure modes). Plus `tip` / `warning` / `details` where they earn their place.
6. `heading` **"Try it with AI"**: at least one `prompt` block the learner copies into any assistant (ChatGPT, Claude, Gemini: never assume one), then what to look for in the answer and one way it may mislead. Early modules: explain it simply, give another example, quiz me, "do not give me the answer; ask me questions". Later modules: generate, then explain line by line, then review the design. Never tell the learner to paste secrets or personal data.
7. **Key takeaways**: exactly one `takeaways` block (2 to 6 items), the last teaching block.
8. **Activities** after the takeaways, at least **two** per lesson **of different kinds**, ids `<lesson-id>-<kind>-<n>`, three progressive hints each, an explanation, and notes that explain a wrong choice without giving the answer away. The owner's menu (use the ones that fit; across a module use many kinds): identify which parts of a scenario become classes (`scenario` or `match`), match objects with their properties and methods (`match`), predict the output of object-oriented code (`predict-output`), identify an encapsulation violation (`fix-bug`/`scenario`), choose between inheritance and composition (`scenario`), identify correct use of polymorphism (`scenario`), complete a missing class implementation (`fill-blank` with a `bank`), fix an incorrectly designed class (`fix-bug`), match SOLID principles to real problems (`match`), refactor poorly structured code (`code-challenge` with tests, or `arrange`), design class relationships from requirements (`arrange` of diagram lines or `scenario`), and `code-challenge` where the learner writes a small class that passes tests. **JavaScript activities are executed by the validator**: run everything. A `fix-bug`/`fill-blank`/`code-challenge` with tests must fail for every wrong option and the starter must not already pass. TypeScript, Java, Python and C# activities are **not** executed: run the code yourself (TypeScript with the repo's `typescript` under `--strict`; the others only if you have the runtime) and store the true output or error text; otherwise use a `scenario`/`match`.
9. **Quiz** (the knowledge check): 3 to 5 shared questions that test understanding and application, never trivia, never "all of the above", plus the level-tagged `-q5` / `-q6` (ADAPTATION_BRIEF). Vary the correct answer's position, the right answer is not the longest choice, every question is answerable from the lesson.
10. **Task** (5 to 20 minutes on paper or in any free JavaScript environment) plus `taskExtra` for levels.

Length: 500 to 900 words of explanation per lesson (up to about 1,100 for the first lesson on a hard idea), `minutes` 15 to 30. **Teach before you ask:** every term, keyword or built-in a quiz question, activity or challenge uses must have been taught in this or an earlier lesson (syllabus order; you may rely on every earlier lesson of the course and of Programming Fundamentals, and **never** on a later one). If a lesson needs a later idea, show it as a black box ("this line creates an object; the next lesson explains how") or leave it out. Do not re-teach an earlier lesson: refer to it by name.

## Voice and content rules

- English only. Do not write Tagalog or Filipino text (a standing owner rule; the app's Tagalog is switched off). Examples may use pesos, jeepney fares, sari-sari stores, load top-ups, school records, barangay events, Filipino names; never real people or companies' private data, never stereotypes; stay neutral where the idea is global.
- Second person, short paragraphs, a patient teacher. No Tali dialogue or mascot references. No jargon without a definition. Intermediate content, but still one new idea at a time, a small example before a big one, hints before answers. Learners read this on a phone: keep code lines short (about 60 characters), classes small (under about 30 lines per block, build up in steps).
- **Accuracy is the first rule.** Run every JavaScript example with `node` (a current LTS) and keep the real output. Be exact about **language differences** and never imply JavaScript has what it lacks: it has `class` syntax over prototypes; `#private` fields and methods (real privacy), and a `_name` convention (not private); **no** `abstract` keyword, **no** `interface` keyword, **no** method overloading (a later definition replaces an earlier one; overloading is emulated with argument checks or default/rest parameters), **no** multiple inheritance of classes (a class has one parent; mixins and composition are the substitutes), **no** access modifiers (`public`/`protected`/`private` are TypeScript, erased at runtime, so they do not protect data when the code runs). Say plainly what TypeScript checks at compile time and what still happens at runtime. For Java, Python and C# comparisons, state only what you are sure of; verify on the official language documentation (WebFetch/WebSearch via `ToolSearch` with `select:WebFetch,WebSearch`; hosts allowed are in `src/features/courses/lib/path-rules.ts`, say in your report if you need another). The course is not `volatile`, so a `version` note is optional, **except** every statement about a product, tool or TypeScript/ECMAScript feature that depends on a version, which gets a `version` note with `checked: '2026-11-16'`, official https sources you opened, no price figures. Never invent a URL, version, quote or statistic.
- **JavaScript style:** `const` by default, `===`, template literals, semicolons, 2-space indentation, `class` names PascalCase, methods camelCase, private members `#name`, `console.log` for output (each call is one output entry in the runner). Money is whole pesos as integers (say so once; floating-point money is a Programming Fundamentals lesson). No `Date`, no async, no modules/`import`, no DOM in runnable activities; check `src/features/code-runner/` before using a built-in (`Map`, `Set`, `Object.freeze`, `Symbol`, `JSON.stringify`, array methods, `structuredClone`, `Object.getPrototypeOf` etc.). **Testing without a test framework:** the course teaches a tiny `assert`-style helper written in plain JavaScript (Programming Fundamentals already did); use that, never Jest in a runnable activity.
- Code blocks are syntax-checked (the real parser, `catalog/code-blocks.test.ts`): a deliberate fragment or pseudocode needs the word `fragment` or `pseudocode` in its `label`, or language `text`. TypeScript blocks must parse as TypeScript; Java/Python/C# comparisons go in `text` blocks or `details` unless the language is checked (JavaScript, JSX/TypeScript/TSX, JSON, Python and bash blocks are parsed: a Python block must be valid Python). Escape `${` and backticks inside TypeScript strings.
- Do not copy text from docs, books or the three curriculum references the owner named (HEC, Coursera): explain in your own words with your own examples.
- **Design honesty:** teach OOP as a tool with costs, not a religion. Show where it helps and where it hurts; React and React Native use functional components and hooks and not every modern app should be class-based; never imply otherwise. Do not present a design as the only right one: say "a reasonable design" and why.

## Modules: days, projects and content notes

Every lesson of the course is JavaScript-first. "Running thread" names the example the module uses so the course feels connected.

**1. Introduction to OOP** (days 1-4; project p1 "Bank account, two ways": the learner reads a short procedural bank-account program and an object-oriented one, writes down what changes when a new rule arrives (a withdrawal fee, a second account type) in each, and explains which they would rather maintain). L1 what OOP is and the problem it solves (growing programs, scattered data and functions, the "software crisis" kept to two honest sentences), objects as things with state and behavior, a first tiny class shown as a black box; L2 procedural vs object-oriented on the same bank problem, side by side (a `table` plus two runnable programs; neither is "wrong"); L3 the four pillars at overview depth only (one paragraph and one example each, a diagram tying them together; later modules teach each in depth: do not go deep); L4 real-world uses (an app screen, a game, a shop, a bank, in words; a table of where objects appear), the honest advantages and disadvantages (reuse, organisation, modelling vs boilerplate, over-engineering, hidden state, deep hierarchies) and a decision guide for when to use OOP, functional style or plain functions. Level: this module may have a few `{ max: 'beginner' }` blocks that redo "what a function/object is" in one paragraph. No `this` yet except inside the black-box class.

**2. Classes and Objects** (days 5-10; project p2 "Student Management System": a `Student` class with name, grade level and a list of scores, methods to add a score, compute the average and report a status; a `Classroom` collection kept as a plain array of students at this stage). L5 objects: state, properties/attributes, behavior/methods; object literals with methods from Programming Fundamentals as the bridge; L6 classes as blueprints, class vs object, instance, a class diagram of `Student`; L7 `class` syntax, `new`, methods, creating the first instances (a short constructor is allowed as a black box: "the next module explains constructors in depth"; use the minimum `constructor(name)` here and say so); L8 several instances with their own state, methods that change state, objects compared by reference not value, what `console.log` shows; L9 `this`: what it points to in a method call, calling a method as a loose function loses `this` (show the real `TypeError`), the arrow-function fix briefly, `bind` named only; L10 the guided build of the Student Management System (requirements in plain words, the class step by step, the tests, the trace of a run). Reuse the visual `classes-objects`.

**3. Constructors and Object Initialization** (days 11-17; project p3 "Product class": a `Product` with a constructor, defaults, validation, a static counter or id generator, a `describe()` method and a discount method). L11 what a constructor is and when it runs, why an object should start valid; L12 parameters, default values, destructured options object for many parameters, argument checking; L13 instance properties vs methods on the prototype, initialization order, class fields (`count = 0;`), derived values set in the constructor; L14 `static` properties and methods, shared across the class, what `this` is in a static method, static factory methods, when static is a smell (global state); L15 the object lifecycle: creation (`new`), use, references, becoming unreachable and being garbage collected (JavaScript has no destructor: say so; explain cleanup by explicit `close()`/`dispose()` methods, honestly and briefly; contrast with C++/Java/Python/C# in a table you have verified); L16 factory functions vs classes (closures for privacy, no `new`, no `this`; when each fits; the trade-off table; both runnable), L17 prototypes: what `class` is syntactic sugar over, the prototype chain, `Object.getPrototypeOf`, method lookup, `hasOwnProperty`/`Object.hasOwn`, why methods are shared and fields are not (a diagram of the chain; a trace table of a method lookup). Keep it to what helps understanding class behaviour; no prototype hacking.

**4. Encapsulation** (days 18-23; project p4 "Bank Account that protects its balance": `BankAccount` with a private balance, validated `deposit`/`withdraw`, an insufficient-funds error, a read-only `balance` getter, a transaction history that cannot be edited from outside). L18 what encapsulation is and why (bundle data and the methods that guard it; control how state changes; the "invariant" idea in plain words: a balance never negative); reuse the visual `encapsulation`; L19 data hiding: public vs private, the `_name` convention (not private) vs real `#private` fields and methods in JavaScript, what happens on outside access (the real `SyntaxError`/`undefined` behavior; check the runner), private methods; L20 getters and setters (`get`/`set`), computed properties, read-only properties, when a plain method is clearer, do not write a getter and setter for every field (that is not encapsulation); L21 TypeScript access modifiers `public`/`private`/`protected`/`readonly`, parameter properties, **compile-time only** (erased at runtime) vs JavaScript `#` (runtime), a comparison table with Java and C# (`private` there is enforced at runtime too: be exact); L22 protecting state: validation in the constructor and setters, defensive copies of arrays/objects returned from a getter, `Object.freeze` limits (shallow), returning copies, throwing meaningful errors (preview of Module 11's error lesson); L23 guided build of the Bank Account project.

**5. Abstraction** (days 24-28; project p5 "Payment processing abstraction": a `PaymentProcessor` contract and two or three providers, a `Checkout` that takes any provider and never sees a provider's internals). L24 what abstraction is, abstraction vs encapsulation in one clear comparison table and one analogy (a TV remote vs the wiring), reuse the visual `abstraction`; L25 hiding implementation details behind a public interface: the interface is the promise, the implementation can change (show a class whose internals change while callers stay untouched); L26 abstract classes and abstract methods: JavaScript has no `abstract` keyword, so show the convention (`new.target === Shape` check, a method that throws "not implemented") and TypeScript's real `abstract class`/`abstract` methods, what each prevents and when; L27 interfaces in TypeScript (`interface`, optional/readonly members, a class that `implements`), duck typing in JavaScript, and designing simple understandable APIs (small surface, clear verbs, no leaking internals, sensible defaults, consistent naming, errors that explain); L28 guided build of the payment abstraction (never real payment credentials; everything simulated; a `version`-free design).

**6. Inheritance** (days 29-34; project p6 "Employee Management System": `Employee` base class and `Manager`, `Engineer`, `Intern` (or similar) with shared and specialised behavior, a payroll report using only the base type; the learner must also explain one place they chose *not* to inherit). L29 what inheritance is: is-a, parent/child, base/derived, superclass/subclass terms (all synonyms, state it), `extends`, what a child receives; reuse the visual `inheritance`; L30 `extends`, `super(...)` in the constructor and `super.method()`, method overriding, the rule that `super()` must run before `this` (the real `ReferenceError`), `instanceof`, calling the parent's version; L31 types of inheritance (single, multilevel, hierarchical, and why multiple/hybrid are not available for classes in JavaScript, Java and C#, with mixins/interfaces as the substitutes; Python's multiple inheritance mentioned accurately) and inheritance hierarchies (inheritance trees as `classDiagram`, how deep is too deep); L32 advantages (reuse, a common type, specialisation) and disadvantages (tight coupling, fragile base class, inheriting what you don't want) honestly, a decision table; L33 when inheritance becomes a problem: the Square/Rectangle and the Penguin/Bird examples, deep trees, "is-a" that is really "has-a", changing a base class breaks children; the learner sees it break and fixes it by composition (previewing Module 8 without teaching it); L34 guided build of the Employee system.

**7. Polymorphism** (days 35-39; project p7 "Notification system": a `Notifier` contract, `EmailNotifier`, `SmsNotifier`, `PushNotifier` and a `NotificationService` that sends through any of them; adding a fourth channel must need no change to the service). L35 what polymorphism is ("many forms"), the same message to different objects, reuse the visual `polymorphism`; L36 compile-time (static) vs runtime (dynamic) polymorphism, **method overloading**: exact about languages: Java and C# have it; JavaScript does not (a later method with the same name replaces the earlier: show it run), emulated with argument checks, default or rest parameters; TypeScript has overload *signatures* with one implementation; Python has no overloading (keyword/default arguments, `functools.singledispatch` named only); L37 dynamic method dispatch (which method runs is decided by the object's real class when the call happens: a sequence diagram and a trace table of a loop calling `speak()` on a mixed array), polymorphism through interfaces/duck typing (no inheritance needed); L38 writing flexible code: replacing long `if/else` or `switch` on a type with polymorphism, programming to a contract, the open-for-extension idea previewed (Module 10 names it), when a plain `switch` is still fine, `instanceof` checks as a smell; L39 guided build of the notification system.

**8. Composition and Object Relationships** (days 40-45; project p8 "Order Management System": `Customer`, `Product`, `OrderItem`, `Order`, a `PaymentService` injected into `Order` or `Checkout`; totals, adding/removing items, paying, and a class diagram that uses each relationship type correctly). L40 composition: an object made of other objects, has-a vs is-a, delegation, why it is flexible; L41 association, aggregation and composition (UML meanings, lifetime ownership: does the part outlive the whole?, `-->` `o--` `*--`, one runnable example of each, an honest note that aggregation vs composition is a design judgement and that many teams use only association and composition); L42 dependency relationships and object collaboration (one object uses another only for a moment: `..>`; objects sending messages, a sequence diagram of Order, Item, Payment; the law-of-Demeter idea in plain words, not by name unless you teach it); L43 dependency injection fundamentals: pass collaborators in (constructor injection), default implementations, a fake/stub for testing, no frameworks or containers, why `new` inside a class hides a dependency; L44 composition vs inheritance: the same feature built both ways, a decision table, "favor composition over inheritance" as a guideline with its limits, mixin/strategy only by name; L45 guided build of the order system.

**9. Interfaces and Abstract Classes** (days 46-50; project p9 "Reusable storage service": a `StorageProvider` contract with `save/load/remove`, an in-memory provider and a simulated file/cloud provider, a `NoteApp` that depends only on the contract; swap providers without changing the app). L46 what an interface is and why it matters (a contract of what, not how; consumers depend on the shape), JavaScript vs TypeScript: conventions and runtime behaviour (duck typing, checks like `typeof obj.save === 'function'`, a `Symbol`-free approach) vs compile-time `interface`; be explicit that TypeScript interfaces vanish at runtime; L47 defining and implementing interfaces in TypeScript (`implements`, optional members, extending interfaces, interface vs `type` named briefly, structural typing: a class need not say `implements` to fit) and the JavaScript equivalent with a runtime guard; L48 abstract classes vs interfaces (shared code and state vs a pure contract), when to choose each, a class implementing several interfaces (multiple implementation, the way around "no multiple inheritance"), the default-method idea in Java/C# named accurately; L49 dependency on abstractions: high-level code depends on the contract, the idea previewed for Module 10's last principle; designing extensible systems (a plug-in style example: adding a provider touches no existing class), the cost of too many abstractions as an honest warning; L50 guided build of the storage service.

**10. SOLID Principles** (days 51-56; no project, each lesson has a refactoring exercise). Each of L51-L55 follows the same inner order inside the standard ten-part shape: the problem the principle solves, **a poorly designed example** (real, runnable, the kind of code people really write), **why it is problematic** (show the pain: add a requirement and watch the change ripple), **the refactor into a better design** (runnable, before/after as two code blocks and a before/after `diagram`), and a practical exercise (a `code-challenge` or `fix-bug`). Teach recognition of problems, not memorisation: every lesson starts from a symptom ("I change one thing and three classes break"), never from the principle's name, and ends by naming the principle. L51 Single Responsibility (a class that formats, saves and emails an invoice; "reasons to change" as the test); L52 Open/Closed (a `switch` on a shape or discount type that grows with every new case; extension by adding a class, not editing; the honest limit: do not abstract before a second case appears); L53 Liskov Substitution (Rectangle/Square or Bird/Penguin; the substitution test in plain words: can a child be used anywhere the parent is, without surprises?; contracts: pre/postconditions as plain sentences; fixing by redesign); L54 Interface Segregation (a fat `Worker`/`Machine` contract that forces `fax()` onto a printer-only class; small role interfaces; in JavaScript by small duck-typed roles and in TypeScript by split interfaces); L55 Dependency Inversion (a high-level report class that creates a concrete database/email class with `new`; invert by depending on a contract and injecting; link to Module 8's injection; do not confuse with dependency injection: be exact: DIP is the principle, injection a technique); L56 applying SOLID: a single messy 60-line module that breaks several principles, the learner finds each smell, decides which fix is worth it (and which is over-engineering), a "SOLID is guidance, not law" discussion, the scenario/match activities that pair real problems with principles. Reuse earlier module examples only as a different angle, never repeat a lesson.

**11. Writing Maintainable Object-Oriented Software** (days 57-63; project p10 "Refactor a poorly structured application": the learner receives a deliberately tangled order/inventory script of about 80 lines with a god class, duplicated logic, deep inheritance and no tests; they split it into small classes with clear responsibilities, write tests first for existing behavior, refactor in small steps keeping tests green, and explain every step; the starting code lives in the project text/steps as a runnable `code` block). L57 coupling (tight vs loose, content/data/stamp coupling named by example not by label, how to loosen: contracts, injection, events by name; a before/after dependency diagram); L58 cohesion and separation of concerns (a class whose methods all serve one purpose; layers: model, logic, storage, presentation as an idea, a diagram; high cohesion + low coupling together); L59 single-purpose reusable classes and avoiding god objects (how a god object grows, the symptoms, how to split it, naming as a design tool); L60 avoiding deep inheritance (a rule of thumb, flattening a hierarchy by composition) and organising files and modules (one class per file by convention, ES module `import/export` shown as `text`/`fragment` blocks only because the runner has no modules, folder layout by feature vs by layer, barrel files named with their cost, circular imports as a smell); L61 error handling in OOP (exceptions vs return values, custom `Error` subclasses with `name`, `cause`, `try/catch/finally`, failing fast, not swallowing errors, error messages for people vs for logs, keeping an object valid after a failed call; all runnable); L62 unit testing classes (what a unit is, arrange-act-assert, testing behavior not private internals, test doubles written by hand: a fake and a stub, testing error paths, why encapsulation and injection make testing easy; the tiny assert helper from Programming Fundamentals in runnable code; a `fragment`-labelled look at how a real test runner's `test`/`expect` reads; no framework installation); L63 refactoring: what it is (change structure, not behavior), tests first, small steps, named refactorings (extract method/class, move method, replace conditional with polymorphism, inject dependency), when not to refactor, and the guided project.

**12. OOP in Real-World Application Development** (days 64-68; no project). ## What every module may assume earlier modules taught

Module n assumes modules 1 to n-1 in full and nothing from module n+1 on. Concretely: `class`, `new` and a minimal constructor appear first in module 2 (module 1 shows only a black-box class); `#private` first in module 4 (earlier modules do not use it); `extends`/`super` first in module 6; `abstract`, TypeScript and `interface` first in module 4/5 (module 4 L21 introduces TypeScript in two sentences with a small example before using it; assume nothing else about TypeScript); dependency injection first in module 8; custom `Error` classes appear lightly from module 4 as a `throw new Error(...)` and are taught properly in module 11; sequence diagrams first in module 7; the tiny `assert` helper is used from module 2 on as a reminder of Programming Fundamentals.
