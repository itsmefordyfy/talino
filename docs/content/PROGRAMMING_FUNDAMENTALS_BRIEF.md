# Programming Fundamentals: brief for module writers

**Course:** `programming-fundamentals`, "Programming Fundamentals: Think Like a Programmer" (beginner, 60 lessons in 12 modules).
**Owner's brief (2026-11-16):** teach learners the core ideas they need to understand how software works, solve problems logically, read code,
and work with AI coding tools. Concept-first, language-independent, practical and AI-assisted. JavaScript is the practice language (the in-app
code runner executes it); say so, and say the ideas carry to every other language. This is the **one deliberate exception** to Talino's
"no standalone programming course" rule: understanding logic is what lets a learner direct, read and judge AI-written code. So it is not a
JavaScript course: teach each idea, show it in JavaScript, and connect it to reading and directing AI output. No browser, DOM, framework,
HTML, Node-only API or backend (other Talino courses cover building with those).

You write ONE module. **First read, in this order:** `docs/content/WRITING_BRIEF.md` (the lesson contract, activity rules, accuracy rules; its
"DIRECTION" paragraph about AI-first still holds: here the technology is JavaScript as a teaching language), `docs/content/ADAPTATION_BRIEF.md`
(five learner levels: this course's audience is mostly complete beginners and beginners, but every lesson still needs the level pieces),
`src/features/courses/content/types.ts`, `lib/lesson-structure.ts`, `lib/standard-rules.ts`, `src/features/activities/types.ts` and `lib/validate.ts`,
the in-app runner `src/features/code-runner/` (what it supports), and one finished beginner-friendly course for craft:
`src/features/courses/content/catalog/courses/ai-coding-beginners.ts` and, for code-challenge style, the archived
`docs/content/archive-programming-courses/programming-fundamentals.ts.txt` and `computational-thinking.ts.txt` (raw material: you may adapt
ideas, never paste; your lessons are different and use the structure below).

## The shape of every lesson (the owner's ten parts)

Each lesson's `body` is, in this order (headings are literal strings so a learner always finds the same parts; the structure test enforces them):

1. **Opening paragraph**: what this lesson is about and why it matters to someone who will build with AI (the lesson must open with a `paragraph`). `intro.objectives` (2 to 4, verb-first) and `intro.why` carry the learning objectives.
2. `heading` **"A real-world picture"** then a paragraph or two: an everyday analogy (a sari-sari store, a jeepney route, a recipe, a queue, a group chat, a school bell). Keep it honest: say where the analogy stops working.
3. `heading` **"How it works"** then the concept explained plainly, **why before how**, one idea at a time, terms defined at first use. Include a visual wherever it teaches: a `diagram` (Mermaid flowchart/sequence, or a JSON spec) or a `visual` from the library (`variables-data-types`, `operators`, `conditionals`, `loops`, `functions`, `arrays-objects`, `scope-execution-flow`, `big-o-growth`, `se-git-branching`, `web-api-request-trace`, `web-client-server`, `web-frontend-backend`, `ai-model-input-output`, `ai-tokens`, `ai-llm-workflow`, `se-sdlc` and the other ids in WRITING_BRIEF; the check rejects an id that does not exist) or a `table`. A diagram must show a real mechanism, never decorate.
4. `heading` **"See it in code"** with `code` blocks (language `javascript`, built in small steps, never a wall), then `heading` **"Walk through the code"**: what happens line by line when it runs (a `list` or paragraphs; for loops and state, a step-by-step trace table with `table`). Lessons that show no code (module 1 and 2, parts of module 10) replace these two headings with **"Walk through an example"** (for example tracing an algorithm step by step on paper). The structure test accepts either pair.
5. Level pieces (see ADAPTATION_BRIEF): a plain-language block `audience: { max: 'beginner' }` right after the concept it explains and a depth block `audience: { min: 'advanced' }`. Also `tip` / `warning` / `details` blocks where they earn their place.
6. `heading` **"Try it with AI"**: the AI-assisted exercise. At least one `prompt` block the learner copies into any AI assistant (ChatGPT, Claude, Gemini: the learner may use whichever they have; teach the tool only as far as this lesson needs, never assume it), followed by a short paragraph or list on **what to look for in the answer** and one way the answer might mislead (an AI can be confidently wrong). Early lessons use "explain it in plain words / give me one more example / quiz me"; later lessons use "generate, then explain line by line, then find the bug". Never tell the learner to paste secrets or personal data. Do not hand over exercise answers through the prompts: ask the AI to guide, hint and check, not to solve (write prompts like "Do not give me the answer; ask me questions").
7. **Key takeaways**: exactly one `takeaways` block (2 to 6 items), the last teaching block: the lesson summary.
8. **Activities** after the takeaways (they are drawn after the quiz): at least **two** per lesson, of different kinds, with ids `<lesson-id>-<kind>-<n>`, three hints each, an explanation, and `wrongNotes`/feedback that explain a mistake without giving the answer away. Use the owner's list as a menu: sequencing/arranging steps or pseudocode (`arrange`), predict the output (`predict-output`), spot the incorrect line (`fix-bug`), complete missing code (`fill-blank`), trace variable values step by step (a `fill-blank` or `predict-output` over a trace written in a `code` block, because there is no separate trace kind: the learner fills in what each variable holds after each line), the result of a condition, how many times a loop runs (`predict-output`), match concepts with real-world situations (`match`: situation to concept, never repeating a printed list), debug broken code (`fix-bug`), build a flowchart from shuffled steps (`arrange` with `language: 'text'`: the lines are the flowchart's steps in order, with decisions written as "IF ... THEN ..." lines), choose the better decision (`scenario`), and `code-challenge` once functions or output-only challenges make sense (output-only until functions are taught; check WRITING_BRIEF "in-app JavaScript runner"). Every activity must be real: the validator runs JavaScript, so run everything.
9. **Quiz** (the knowledge check): 3 to 5 shared questions that test understanding and application, not recall, plus the level-tagged `-q5` / `-q6` questions (ADAPTATION_BRIEF). Vary the correct answer's position; the right answer is not the longest choice; every question answerable from the lesson.
10. **Task** (the hands-on activity: 5 to 20 minutes on paper or a laptop, anything runnable by the learner in any free JavaScript environment or on paper) plus `taskExtra` for levels.

Length: 500 to 900 words of explanation per lesson (up to about 1,100 for a first lesson on a hard idea), `minutes` 15 to 30. Teach before you ask: every term, operator or built-in used in a quiz, activity or challenge must have been taught in this or an earlier lesson of the course (the order is the syllabus order; **you may not use any idea that a later lesson teaches**, and you may rely on every earlier lesson). If a lesson needs an idea that comes later, show it as a black box ("this line prints a value; the next module explains how") or leave it out. Do not re-teach an earlier lesson: refer to it by name.

## Voice and content rules

- English only. Do not write Tagalog or Filipino text (a standing owner rule). Examples may use pesos, jeepney fares, sari-sari stores, load top-ups, school quizzes, barangay events and Filipino names, never real people or companies' private data, never stereotypes; stay neutral where the idea is global.
- Second person, short paragraphs, a patient teacher. No Tali dialogue or mascot references. No condescension, no jargon without a definition. Beginners first: one new idea at a time, small example before a big one, hints before answers.
- **Accuracy is the first rule.** Run every JavaScript example with `node` and keep the real output; the in-app runner is a subset, so also let the validator run activities. Verify every claim about a tool, command or standard on official pages (WebFetch/WebSearch: `ToolSearch` with `select:WebFetch,WebSearch`). Allowed documentation hosts are in `src/features/courses/lib/path-rules.ts`; if you need another, say so in your report. Where a statement depends on a product or version (an AI assistant's features, Git, JavaScript's behaviour that changed), add a `version` note with `checked: '2026-11-16'`, official https sources you opened, and no price figures. Name tools by what the learner sees today, and teach the stable idea.
- Never invent a URL, version, quote or statistic. Say what is uncertain or leave it out.
- JavaScript style for the course: `const` by default, `let` when a value changes (never `var` except to explain what it is, and only if your module needs it), `===` never `==` except to teach the trap, template literals for text, semicolons, 2-space indentation, `console.log` for output. Each `console.log` call is one output entry in the runner. No `prompt()`, no `Date`, no async, no modules, no classes, no DOM; check `src/features/code-runner/` for what runs (and whether `Set`, `Map`, `switch`, `do/while`, `for...of`, array methods work before you use them in an activity or challenge).
- **Running example thread:** the personal expense tracker. Whenever an example fits, use expenses shaped `{ description: 'Jeepney fare', amount: 24, category: 'transport', date: '2026-11-16' }` (amounts in whole pesos or centavos as an integer when the lesson is about money precision; dates as plain strings). Do not build the final project early: its lessons are module 12.
- Code blocks are syntax-checked (the real parser): a deliberate fragment or pseudocode needs the word `fragment` or `pseudocode` in its `label`, or language `text`. Escape `${` and backticks inside TypeScript strings.
- Beginners must never see a wall of code: build up in steps, explain every line.
- Do not copy text from docs or books; explain in your own words.

## Project of the module

When your module has a project, set `project` (id `programming-fundamentals-p<N>`; the numbers are fixed below). A project has `title`, `summary`, `outcome`, `unlockAfterDay` (the day of your module's last lesson, or the lesson before it if the last lesson introduces the project), 3+ `steps` (ids `<project-id>-s<n>`; at least one with an `audience`), a text `submission` (the learner pastes pseudocode, a flowchart written as text, or code and their explanation), a `rubric` of 3 to 6 and a `rubricExtra` for levels. The owner's assessment aims: understanding, not memorisation: ask the learner to **explain** their choices in the submission. Project ids by module: 1 -> p1, 2 -> p2, 3 -> p3, 4 -> p4, 5 -> p5, 6 -> p6, 7 -> p7, 8 -> p8, 9 -> p9, 10 -> none, 11 -> p10, 12 -> p11.

## Module notes

1. **Understanding Programming** (lessons 1 to 4; project p1: "Order food as instructions": the learner writes the steps of ordering food (or buying load) precise enough for a literal-minded machine, then lists what could go wrong). Lesson 1: what a program is, instructions, why "think like a programmer", and a first exercise: ordering food in exact steps (a human fills in the ambiguity a computer cannot). Lesson 2: the CPU's fetch-decode-execute idea in plain words, memory, input and output, instructions run in order, a computer does exactly what it is told. Lesson 3: what a programming language is (a precise way to write instructions), syntax and meaning; how an application is made: frontend, backend, database, full-stack, in words and one diagram, with no web tutorial. Lesson 4: how AI is changing software development: what AI assistants do well and badly, why fundamentals matter more not less, the learner's role (direct, read, judge, test), honest limits; dated version notes for statements about tools. No JavaScript is required in module 1; if you show a line it is a black box. Use "Walk through an example" headings.
2. **Computational Thinking and Problem Solving** (lessons 5 to 10; project p2: "Design an expense calculator": pseudocode and a flowchart in text for a calculator that takes a list of expenses and prints the total and the biggest). Decomposition, patterns, abstraction, logic (and, or, not as thinking tools), inputs/processes/outputs, algorithms (precise, finite, ordered, with a clear end), pseudocode (plain conventions: SET, IF/ELSE, REPEAT, PRINT, as plain text; use `language: 'text'` and label `pseudocode`), flowcharts (Mermaid flowchart diagrams for start/end, process, decision, with `(rounded)` start and end nodes), and testing an algorithm by hand before coding ("dry run" with a trace table). Little or no JavaScript: arrange activities with `language: 'text'`, scenario, match, tap-reveal, fill-blank over pseudocode with `bank`.
3. **Variables, Constants and Data Types** (lessons 11 to 15; project p3: "Model a user profile": a table of fields with name, type, example, constant or changing, and a short JavaScript object-free description using separate variables). First JavaScript. Variables as labelled boxes (and where the box analogy breaks), declaring and assigning, `let` vs `const`, naming rules and conventions (camelCase, meaningful names, no reserved words), integers vs floating-point (and why `0.1 + 0.2` is not exactly `0.3`, handling money as integer centavos), strings, booleans, `null` and `undefined` and the difference, type conversion (explicit `Number()`, `String()`, `Boolean()`, implicit coercion traps), dynamic vs static typing (JavaScript is dynamic: say what a static language does differently, one tiny pseudo-example in another language labelled as such). Arrays and objects come in module 8: here the profile is separate variables and a table.
4. **Operators and Expressions** (lessons 16 to 20; project p4: "Shopping cart total and discount": logic for a cart with quantities, a discount rule and a total). Arithmetic (`+ - * / % **`), assignment (`= += -= ++ --`), comparison (`=== !== < > <= >=`; `==` only as the warned-about trap), logical (`&& || !`, truthy and falsy), precedence and parentheses, expressions vs statements, string concatenation, template literals, `.length`, a few basic string operations (`toUpperCase`, `trim`, `includes`, `slice`: check the runner supports them), and the common mistakes (`=` vs `===`, string `"5" + 3`, integer division expectations, floating-point comparisons, off-by-one reasoning, operator precedence surprises). Conditions are module 5: do not use `if` here (use expressions and printing booleans) except in the project, which may be written as pseudocode with IF.
5. **Conditions and Decision-Making** (lessons 21 to 25; project p5: "Login validation and eligibility checker"). Boolean logic and truth tables, `if`, `else`, `else if`, nesting, combining conditions, `switch`/`case` with `break` and the fall-through trap, ternary only briefly in a `details`, guard clauses and early returns shown **without functions** (use a flag variable and say functions come later) or defer; avoiding complex conditionals (name the condition in a boolean variable, flatten nesting, lookup instead of long chains). Login checks use fixed example values, never real passwords; say that real sign-in is never built from scratch.
6. **Loops and Repetition** (lessons 26 to 30; project p6: "A number guessing game": the program plays against a fixed list of guesses, since the runner has no input; plus a variant for repetitive-task automation like printing a week's budget table). `for`, `while`, `do/while` (check the runner; if unsupported show it as a non-runnable block with a label and use `fix-bug`/`match` instead of running it), nested loops (patterns, multiplication tables, grids), `break`, `continue`, infinite loops (why they happen, how to spot them, loop guards), common mistakes (off-by-one, wrong update, modifying the counter, condition never false). Predict how many times a loop runs; trace tables for state.
7. **Functions and Reusable Logic** (lessons 31 to 35; project p7: "A reusable calculator" with one function per operation and one that chooses). Definition, calling, parameters vs arguments, return values vs printing, scope (local and global, shadowing, why globals cause bugs), composition (output of one function as input of another), small single-purpose functions, default parameters briefly, recursion (base case, recursive case, call stack picture, factorial, countdown; when a loop is better). From now on `code-challenge` with function-style tests is allowed.
8. **Data Structures Fundamentals** (lessons 36 to 40; project p8: "Inventory management logic": add, remove, update stock and list low-stock items). Arrays/lists (index starting at 0, `length`, `push`, `pop`, `shift`, `unshift`, `splice`/`slice`, `indexOf`/`includes`; verify in the runner), looping through arrays (`for`, `for...of`, `forEach`, plus `map`/`filter` introduced gently, whichever the runner supports), objects as key-value pairs (dot and bracket access, adding, deleting, looping over keys), `Set` and `Map` basics (unique values; keyed lookups with any key), choosing the right structure for a problem (a table: order matters, uniqueness, lookup by name, counting), arrays of objects (the expense list shape) and a first look at "time" (why lookup by key beats scanning, in words, no Big-O jargon beyond one mention).
9. **Reading, Debugging and Testing Code** (lessons 41 to 46; project p9: "Fix the broken program": a deliberately broken program (about 25 lines, with one syntax error, one runtime error and one logic error) to be found and fixed; the learner submits what they found, how, and the fix). Reading code top to bottom and following execution order (a trace table), the three kinds of error, debugging method (reproduce, narrow, form a hypothesis, test it, fix, confirm; rubber-duck explanation), `console.log` debugging, stack traces (how to read one: the message, the line, the call chain, shown as real Node output pasted into a `text` block you produced by running it), breakpoints and stepping in a browser's developer tools or an editor (conceptual: describe what a debugger does and show a simple stepping table; verify names on official docs, version note), basic tests (a tiny assert function written in plain JavaScript, expected vs actual, test names, one test per behaviour), edge cases (empty, zero, negative, very large, wrong type, duplicate) and validation of input.
10. **How Programming Languages Work** (lessons 47 to 50; no project). Conceptual and beginner-friendly, **not** a computer science theory course: high-level vs low-level, source vs machine code, compilers vs interpreters (and JIT in one sentence), how code runs from file to result, static vs dynamic and strong vs weak typing (with JavaScript examples that show the effect), a simple picture of memory (variables as names for places, values, references vs copies: one small example with arrays), APIs (what an API is, requests and responses, JSON, a real call described and shown in a `text` block produced by running something real or clearly labelled as an illustration, status codes in words; a free public API only if you verify it; no keys), version control and Git (why it exists, commit, branch, merge, remote, a short real command sequence you ran in a scratch repo with its real output; official sources `git-scm.com` and `docs.github.com`; version notes).
11. **Programming with AI** (lessons 51 to 55; project p10: the owner's practical activity: given a simple requirement ("a function that, given a list of expenses, returns the total per category"), the learner asks an AI assistant to generate a solution, asks it to explain the code line by line, asks it to find possible bugs, tests it, and improves it, then submits the prompts, the code, what they found wrong or unclear, and what they changed). Lessons: how coding assistants work (a model predicts likely text from patterns in training data and your context, so it can be useful and wrong; tools that read your files and run commands exist, named only with dated version notes; do not teach one product's UI as the subject), using AI to learn concepts (ask for analogies, ask to be quizzed, ask for a simpler version, check against the lesson), generating code from requirements (write requirements with inputs, outputs, examples and edge cases; ask for a plan first), understanding generated code line by line (a repeatable method, shown on real generated-looking code you wrote and ran), finding bugs and reviewing (a review checklist; writing tests for the generated code; running it; spot incorrect, insecure or over-complicated code), hallucinations (invented functions, wrong outputs, outdated APIs, plausible but wrong explanations; show real examples you can verify), and knowing when not to trust AI (security-sensitive code, money, anything you cannot verify, personal data, licences; the learner remains responsible). Teach AI as a coding partner, never a replacement for understanding. Every claim about AI tools gets a version note, sourced from the tool makers' official documentation, no pricing. Prompts must work with any assistant.
12. **Final Project: A Personal Expense Tracker** (lessons 56 to 60; project p11 is the final project, `unlockAfterDay` 59 because lesson 60 itself reviews and presents it). The one project built incrementally across five lessons, in JavaScript: 56 plan (requirements, data shape, pseudocode, a flowchart as a Mermaid diagram, test plan; no code yet), 57 add and categorize expenses (`addExpense`, categories as a fixed list), 58 store and display and total (an array of expenses, `listExpenses`, `totalOf`, `totalByCategory`), 59 filter and validate and handle invalid values (`filterByCategory`, `filterByMonth`, `validateExpense` returning errors, edge cases), 60 organize, review and explain (clean up names and functions, a small test set, an AI review pass as an optional partner, and explaining the solution in the learner's own words). Every lesson's activities build on the same code and each lesson's code block extends the previous lesson's (show the whole running program at the end of lesson 60). AI help is **optional**: a `details` or `tip` shows how to use AI as a partner at each step, never as the thing that writes the program. The project's rubric assesses problem decomposition, logic, correctness, code organization and the learner's explanation; its steps follow the five lessons.

## What you may assume earlier modules taught (for your own module's order)

Module n assumes modules 1 to n-1 in full and nothing from module n+1 on. The learner knows `console.log` from module 3 (module 1 and 2 use none), has met arrays and objects only from module 8, and `function` only from module 7: any earlier lesson that needs a list or a function shows it as a black box, or uses separate variables and straight-line code.
