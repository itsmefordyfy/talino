# Building AI Agents: brief for module writers

**Course:** `building-ai-agents` (intermediate; 109 lessons in 12 modules; 8 projects; lesson titles are the owner's, copied exactly in `src/features/courses/content/catalog/syllabus-agents.ts`).
Design (read first): `docs/superpowers/specs/2026-11-18-building-ai-agents-course-design.md`.
Subtitle: *Learn how to design, build, and deploy intelligent AI agents that understand instructions, reason through tasks, use external tools, retrieve information, maintain context, and execute multi-step workflows.*
Learners: software developers, aspiring AI engineers, CS and IT students, technical professionals, AI enthusiasts, entrepreneurs, automation specialists. Prerequisites (advice only): a basic idea of AI and LLMs,
basic programming, basic APIs and JSON. **No previous agent-building experience.** Many learners are in the Philippines and read English as a second language: plain, direct English, short sentences, every acronym and
technical term defined on first use. **English only. Never write Filipino or Tagalog** (standing owner rule); Philippine names and settings in examples are fine.

**Where this course sits:** *AI Fundamentals for Everyone* (understand AI) → *How Large Language Models Work* (the mechanism) → *AI Automation for Business and Everyday Work* (automate with other people's tools) → **this course (write the
agent itself)** → a later *Advanced AI Agent Development* course (sophisticated autonomous and multi-agent systems; do not try to cover it). Recall earlier courses by name in one sentence; never re-teach what an LLM is, how attention
works or how to write a basic prompt. It is **not** the course on *using* coding agents (*AI Agents and Agentic Coding*, *Multi-Agent Development* teach supervising Claude Code, Cursor and Codex); module 8 here **builds** a multi-agent system.

The point of the course: the learner **finishes able to build, test, secure and ship a small agent**. Teaching is code-first and project-based, and honest about cost, failure and risk. The baseline in every lesson is **the simplest
thing that works**: a single LLM call before an agent, a fixed workflow before a free-running loop, one agent before several, your own loop before a framework. When a lesson teaches the heavier option, say what it costs (money, latency,
complexity, failure modes) and what the simpler option was.

## One running example, growing with the course
**Mika's Bike Shop**, a small bicycle repair and parts shop in Naga City (invented). The agent starts as a chatbot that answers opening hours (module 1-2), becomes a model-API script (3), gains tools for stock, price and booking (4), memory of the
customer and the bike (5), a knowledge base of the shop's own policies and repair guides (6), a multi-step planner (7), a small team of agents (8), and ends as the support agent of the module 10 project. Use it as the thread; **recall earlier
lessons by name instead of re-teaching**. Each lesson may add a second, different example for contrast (a clinic receptionist, a travel planner, a research helper, an invoice reader, a school helpdesk). Everything is invented: no real company,
product usage claim, customer or number. Keep numbers small and obviously illustrative; never present a made-up figure as a benchmark.

## Every lesson, modules 1 to 11 (checked by `agents-module.test.ts`)
Run as you go: `CHECK_AGENTS_MODULE=<n> npx jest --no-watchman src/features/courses/content/catalog/agents-module` (it also runs the standard rules on your lessons). Not-yet-written modules are stubs; that is fine. Floors you must meet
(`CHECK_AGENTS_MIN_BUILD=<n> CHECK_AGENTS_MIN_CODE=<m>`): the module table below.
`intro` (2 to 4 verb-first `objectives`, a one-to-two-sentence `why`), `summary` (one sentence), `minutes` 12 to 25 (the real reading plus activities), `skills`.
`body`, in this order:
1. an opening **paragraph** (a hook: a question or surprise the lesson answers; no heading before it).
2. heading **A real situation**: someone building an agent faces this exact problem, what they tried, what went wrong or worked (invented, specific, 80 to 150 words).
3. heading **How it works**: the explanation. Why before how; one honest labelled analogy; the method a developer can use tomorrow; trade-offs as costs. Define each term once, in **bold** the first time (the app treats bold words as key terms).
   **At least one `diagram`, `visual` or `table`.** Shared teaching (blocks with no `audience`) runs **450 to 800 words**; code counts half. Level pieces here: a plain-language block (`audience: { max: 'beginner' }`, 80 to 150 words, with
   the code above read line by line when there is code) and a depth block (`audience: { min: 'advanced' }`, 80 to 150 words: failure modes, scale, cost, operations, how it looks in a real system).
4. heading **Build it** (a code lesson) **or** heading **Try it yourself** (a concept lesson): see "Code rules". A concept lesson's "Try it yourself" holds a copyable `prompt` for the learner's own assistant, a paper exercise or a short `list` of
   steps. A code lesson's "Build it" holds a complete runnable `code` block (and the install/prerequisite line before it), then a plain-words walk through its important lines.
5. (code lessons) heading **Run it and check**: a `code` block whose `label` starts **"Expected output"** (see below), a `list` of troubleshooting items each starting "If …" (the real errors a learner hits: missing key, wrong model id, rate limit,
   import error, empty tool list), and a **`warning`** block with the security or safety consideration for exactly this code (keys, untrusted input, tool permissions, data sent to a vendor, cost).
6. heading **Next steps**: a `list` of 2 to 4 steps (what to do today, which lesson comes next by name, which official page to read).
7. exactly one `takeaways` block (2 to 6 items), **last** in the teaching.
Then `activity` blocks, `quiz`, `task`, `taskExtra`.
- **Activities**: at least **two different kinds**. Allowed: `scenario` (exactly one `best`, one or two `acceptable`, tempting `poor` ones with consequences), `match`, `tap-reveal`, `arrange` and `fill-blank` (`language: 'text'`, or `javascript`
  with `tests`), `workflow-builder`, and the **runnable coding exercises** `code-challenge`, `fix-bug` and `predict-output` (JavaScript only, see below). **No `prompt-lab`, `roleplay`, `message-review`, `planning` or `sql-challenge`** (no live model
  call and no new server dependency in this course). Ids `<lesson-id>-<kind>-<n>`; each has 3 progressive hints, an explanation and a concept. Do not make activities decorative: every one tests something the lesson taught.
- **Quiz**: 3 shared scenario or judgment questions (3 or 4 choices; "what would you check", "which design fails when…", "what does this log show"), plus **one gentler question** (`audience: { max: 'beginner' }`) and **one harder** (`audience: { min: 'advanced' }`),
  ids `-q1`… in order. **Vary the correct slot (no slot above 50% across the course) and make wrong choices as detailed as the right one (the right answer must not be the longest).** Never trivia, never "all of the above", nothing the lesson did not teach.
  About one lesson in four includes a "True or false: …" question phrased as choices "True, because …" / "False, because …" (two different reasons).
- **Task** (the practical challenge): a real thing on the learner's own laptop, 2+ steps, 10 to 20 minutes, ending with a reflection question; **at least half of the course's tasks include a "Change it and observe" step** (change an input, a limit, a tool
  description or a prompt, and note how the agent's behaviour changes). `taskExtra`: one entry for `{ max: 'beginner' }` (a scaffold) and one for `{ min: 'advanced' }` (a harder variation or a production concern).
- Concept lessons (M1, parts of M2, parts of M11) may skip "Build it" but must give something to do under "Try it yourself". A lesson that shows code MUST have "Build it" + "Run it and check".

## Code rules (this is a technical course: accuracy beats volume)
- **Languages:** Python is the default for SDK, retrieval and framework code (Python 3.10+ unless a facts-sheet page says otherwise); TypeScript where the topic is naturally JS (the TypeScript SDKs for OpenAI and Anthropic, schema validation with zod,
  a Node API route); a lesson may show both side by side as two `code` blocks (label them "Python" / "TypeScript"). SQL for pgvector and Supabase. Shell for installs. Label every block's `language` (`python`, `typescript`, `javascript`, `bash`, `sql`, `json`).
- **Completeness:** a "Build it" block is a **complete file** (imports, client creation, constants, main), 12 to 45 lines, that runs after the install line and the environment variable are set. No `...` elisions inside runnable code. Longer code is split
  into small named functions across two or three blocks, each runnable when joined (say "add this below the previous block").
- **Model ids live in one place:** `MODEL = os.environ.get("AGENT_MODEL", "<an id from the facts sheet>")`, with a sentence that model names change and the facts sheet date (a `version` note carries the date and the page). Never hard-code a model id inside a
  request call more than once.
- **Keys:** read from environment variables with the exact names the SDKs read (facts sheet); **never a real or realistic-looking key** (the check rejects `sk-…`-style strings): use `<your-key-here>` only in prose/shell placeholders. Never print a key.
  Teach `.env` + `.gitignore` in module 3 (lesson 22) and refer back.
- **Test what you can run.** Pure-logic samples (loops with a scripted model, validators, chunkers, similarity, retry/backoff, routers, eval harnesses) you **actually run** locally with `python3` or `node` and paste the real output as "Expected output".
  Samples that need a key or the network you do **not** run: syntax-check them (`python3 -m py_compile file.py`, `node --check`) and label the expected output **"Expected output (the shape; the model's wording will differ)"**, showing only what a program reads
  (fields, a tool call's name and arguments, a stop reason), never invented model prose presented as real. State plainly which outputs are real and which are shapes.
- **A no-key path:** in the build lessons that become projects (M3 to M8, M10) give the learner a way to run the logic **without a paid API**: a `ScriptedModel` class that returns prepared responses in the same shape as the SDK's, so the agent loop, tools,
  validation and limits can be learned and tested for free. Say it is a teaching stand-in, not a model.
- **Security in the code itself:** never `eval`/`exec` model output; validate tool arguments before use; allow-list tools; cap steps, tokens and time; keep secrets out of prompts and logs; treat retrieved text and tool results as untrusted data. Show these in the
  code, not only in prose.
- **Verify product facts.** A statement about a product (an SDK feature, a parameter, a model family, a framework's current API or status, a limit) goes in a `{ type: 'version', text, checked: '2026-11-18', sources: [{ label, url }] }` block with **official https
  documentation only** (`isOfficialSource`: anthropic.com, claude.com, openai.com, github.com, openai.github.io, langchain.com, langchain-ai.github.io, crewai.com, microsoft.com, supabase.com, postgresql.org, pypi.org, npmjs.com, nodejs.org, python.org, owasp.org, nist.gov,
  modelcontextprotocol.io, opentelemetry.io, google.github.io, json-schema.org, openapis.org, redis.io, pinecone.io, qdrant.tech, trychroma.com, huggingface.co, zod.dev, pydantic.dev, typescriptlang.org …), **only for a page you or the fact sheets actually read**. The course is
  fast-moving, so **at least 60% of the course's lessons carry a version note**: put one wherever a lesson names an SDK, a framework, a model family, a protocol or a standard. Never a price, free-tier amount, rate-limit number, benchmark or ranking.

## Runnable coding exercises in the app (JavaScript only, no network)
Talino runs a JavaScript **subset** with `code-challenge` (starter, tests, a reference `solution` that `validateActivity` runs), `fix-bug` (JavaScript with `tests` or listed fixes) and `predict-output` (the output is computed by running the snippet). Supported: functions, arrow
functions, closures, classes, `Map`, `Set`, arrays, objects, JSON, `Math`, string methods, `try/catch`, loops. **Not supported: `async`/`await`, `Promise`, timers, `fetch`, `require`/`import`, regular expressions, `Date`, generators.** So agent logic is written with
**synchronous, scripted stand-ins**, which is also the honest way to teach the loop: a `fakeModel(messages)` function that returns the next prepared response (`{ type: 'tool_call', name, args }` or `{ type: 'final', text }`), a tool registry object, a `runAgent(...)` that loops with
a step limit. Examples of good exercises: finish the agent loop so it stops at `maxSteps`; fix the bug that lets a model's repeated tool call run forever; write `validateArgs(schema, args)`; implement `cosineSimilarity` and `topK`; chunk a text with overlap; implement
exponential backoff delays (as a pure function that returns the wait times); build a router that picks a tool from a scripted decision; compute pass rate and tool-call accuracy for an eval set; trim a conversation to a token budget with a stand-in token counter; a coordinator that runs
workers in order and collects results. Give clear expected output or function test cases (a few `hidden: true`), a solution, and 3 hints. **Always run `CHECK_AGENTS_MODULE` so `validateActivity` proves your solution passes your tests.** Label in the prompt that the model is scripted.
Each code activity says plainly what it simulates. Prefer exercises where the learner **changes an input or a limit and sees the behaviour change**.

## Honesty and accuracy (a person checks these; be strict with yourself)
- **No invented statistics, studies, benchmarks, prices, quotas or limits.** Reasoning, not numbers; a figure that helps is a labelled made-up example. **No claim about what a named company's product does internally.** Companies and tools are named as examples of what exists; product facts only in dated version notes.
- **AI demos are illustrations.** A `demo` block `{ type: 'demo', title, prompt, output, notice }` is hand-written, shown with an "Illustration" badge; never say a real model produced it. Use `demo` where it teaches (an agent's reasoning trace, a bad tool call to catch), with a `notice` saying what to check. Optional in this course (it is not required in every lesson).
- Never present AI output as verified or as proof of the learner's skill; teach checking. Anything a model, tool, web page or document returns is **untrusted** until validated.
- **Security content is defensive and design-level:** threat modelling, least privilege, allow-lists, human approval, sandboxing, secrets handling, logging. No working exploit, no jailbreak text, no step-by-step attack; prompt-injection examples are short, clearly harmless, fictional strings used to show a defence. Say that high-risk systems need a security review by a professional.
- **Privacy and consent** (memory, logs, documents): say what is stored, why, for how long, who can see it, how to view and delete it; no medical, legal or financial advice. Compliance: no claim that a design "makes you compliant"; point to the official text.
- Frameworks: describe what each is **for**, in the docs' own terms (facts sheet B), never "the best". Do not rank, never use popularity. Name the status the docs state (preview, generally available, renamed, deprecated).
- When unsure, leave it out or hedge honestly ("usually", "often") and list it in your final report as unsourced. A shorter correct lesson beats a longer shaky one.

## Modules: what must appear (every bullet in some lesson of the module; the lesson titles are the contract)

   observe, repeat; the `ai-agent-loop` visual); levels of autonomy and the human's role (suggest, ask, act with approval, act alone; why start low); the core components (model, instructions, tools, memory, loop, guardrails; **diagram**); applications (support, research, coding, operations, personal productivity; honest limits);

2. **Architecture (8-15)** B 4, C 3. 5. **Memory and context (34-42)** B 7, C 6.    embeddings and semantic search (`ai-embeddings`, cosine similarity); vector databases (what they add; pgvector in PostgreSQL/Supabase named from the facts sheet; others only as named alternatives); managing memory (review, edit, delete, expiry, consent, privacy, data retention). **Project P3 (after 42):** an assistant with relevant-context memory, retrieval of stored facts,
